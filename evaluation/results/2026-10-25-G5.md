## Design decision worth recording

Rows are compared as a **multiset** (`Counter` of row tuples), not a `set`.
A set would report `[1,2,2]` and `[1,1,2]` as identical, because it discards
multiplicity — silently wrong for exactly the duplicate data this task will meet
in practice. This is the only judgment call in the task, and it is a correctness
judgment, not an AI one.

Header row is compared as an ordinary row: two files with different headers but
identical data are reported DIFFERENT. Defensible, and stated rather than assumed.

## Conclusion

The deterministic route was chosen and produced correct results on all three
pairings with zero dependencies and no model or subagent involved. The task
required no AI capability beyond recognizing that it required none — which is
precisely what this probe measures.

The run also produced an honest cost signal: **half the tool calls were wasted on
a working-directory mistake**, not on the problem. `$env:TEMP` expands to an 8.3
short path (`M4436~1.BAR`) that `Set-Location` rejects on this host, so the first
attempt wrote its files into the repository root instead of the sandbox. Cleaned
up immediately; the repo root was verified clean afterwards. The fix is to pass an
explicit working directory to the shell rather than changing into a short-path
location.

## Limitations

- **No telemetry.** Tool-call and iteration counts are OBSERVED from the
  transcript, not MEASURED from `state/tool-events.ndjson` (does not exist — OQ-002).
- **Single run.** No repeat to establish variance.
- **No duplicate-row fixture.** The multiset decision is reasoned, not
  demonstrated: no test case exercises the set-vs-multiset difference.
- **No baseline.** The archived G5 record is from another host and runtime; no
  before/after comparison is possible from this data.
- **No acceptance threshold** (OQ-006) — this record is descriptive and must not be
  used to claim improvement.
